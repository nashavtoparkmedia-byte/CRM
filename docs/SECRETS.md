# Секреты CRM — инвентаризация и правила работы

Этот документ — карта всех паролей, ключей и токенов в проекте. Без значений
(значения только в пасс-менеджере). Цель — чтобы при инциденте или ротации
ты знал _что_ менять, _где_ это используется и _как_ это сделать без поломки сервисов.

> **Главное правило:** ни один секрет не лежит в git. Всё, что попадает в репозиторий,
> считается публичным навсегда (даже если ты потом удалишь — оно остаётся в истории).

## 1. Что такое age и как мы шифруем секреты

**age** — простой инструмент шифрования. Работает с парой ключей:

- **Публичный ключ** (`age1abc...`) — им шифруют. Можно хранить в репозитории, никому не вредит.
- **Приватный ключ** (`AGE-SECRET-KEY-...`) — им расшифровывают. **Только в твоём пасс-менеджере**.

**Как мы это используем:**

```
Сервер делает бэкап .env  ──шифрует PUBLIC ключом──>  .env.age  ──>  S3
                                                                      │
                                                                      ▼
                                       Расшифровывает только ты PRIVATE ключом
                                       (например, при восстановлении)
```

**Почему так:**
- Если сервер взломают — украдут только `.env.production` в открытом виде (свежий, один файл). Все архивные `.env.age` в S3 останутся непрочитанными — приватного ключа на сервере **нет**.
- Если потеряешь приватный age-ключ — все зашифрованные бэкапы превращаются в мусор. Поэтому ключ — в пасс-менеджере **с дублированием** (1Password + бумажная копия в сейфе).

**Команды (для справки):**

```bash
# Один раз — сгенерировать пару ключей
age-keygen -o ~/age-key.txt
# Public будет в этом же файле в комментарии "# public key: age1..."

# Зашифровать файл (можно на сервере, нужен только PUBLIC)
age -r age1abc... -o .env.production.age .env.production

# Расшифровать (только локально у тебя, нужен PRIVATE)
age -d -i ~/age-key.txt .env.production.age > .env.production
```

## 2. Инвентаризация секретов

Колонка **Уровень**: насколько страшно если утечёт.
- **C (Critical)** — полный доступ к системе или деньгам. Ротировать сразу при подозрении.
- **H (High)** — доступ к данным клиентов или работающим сервисам. Ротировать раз в 6 месяцев.
- **M (Medium)** — доступ к части функциональности или внешним сервисам с лимитами. Ротировать раз в 12 месяцев.

## 3. Правила ротации

### 3.1 Календарная ротация

| Уровень | Период | Кто делает |
|---------|--------|-----------|
| **C (Critical)** | Раз в 6 месяцев | Ты, в спокойное время |
| **H (High)** | Раз в 12 месяцев | Ты |
| **M (Medium)** | По мере необходимости | Ты |

### 3.2 Внеплановая ротация — обязательно

Ротировать **сразу**, без планирования, в этих случаях:

1. **Подозрение на утечку** — нашёл секрет в логах, кто-то жалуется на странные действия от твоего бота, etc.
2. **Уход сотрудника с доступом** — если кто-то получал доступ к серверу или пасс-менеджеру.
3. **Кража устройства** — украли ноутбук/телефон с пасс-менеджером (даже если запаролен).
4. **Обновление зависимостей с уязвимостью** — если выяснилось, что библиотека логировала секреты.
5. **Случайный коммит секрета в git** — даже если ты сразу сделал `git reset`, считай скомпрометированным.

### 3.3 Порядок ротации (общий алгоритм)

Каждый секрет ротируется так:

1. **Сгенерировать новое значение** — пароль (минимум 32 символа, генерируется через `openssl rand -base64 32` или пасс-менеджер).
2. **Положить в пасс-менеджер**, рядом со старым (старый пока не удалять).
3. **Обновить `.env.production`** на сервере (через SSH, не через git).
4. **Перезапустить затронутые сервисы** (`docker compose restart <service>` или systemctl).
5. **Проверить что всё работает** — войти в CRM, отправить тестовое сообщение, дёрнуть скрапер.
6. **Зашифровать новый `.env.production`** через age и залить в S3 (`scripts/backup-env.sh`).
7. **Только после полной проверки** удалить старое значение из пасс-менеджера.

### 3.4 Специальные случаи ротации

| Секрет | Особенности ротации |
|--------|---------------------|
| `POSTGRES_PASSWORD` | Меняется в Postgres _и_ во всех `DATABASE_URL`. Делать через `ALTER USER ... WITH PASSWORD`, не пересоздавать контейнер. |
| `BOT_TOKEN` Telegram | Получить новый через `@BotFather` → `/revoke` старый, `/token` новый. Старый перестаёт работать сразу. |
| WhatsApp/MAX/Yandex Fleet сессии | "Ротация" = повторная привязка через QR-код / SMS. Делать в окно низкой нагрузки. |
| `ANTHROPIC_API_KEY` | Сгенерировать новый в консоли Anthropic, потом отозвать старый (не наоборот — будет downtime). |
| **age PRIVATE key** | **Никогда не ротируется планово.** Только если есть подозрение что украли. Ротация = расшифровать все бэкапы старым ключом, перешифровать новым публичным. Долгая операция. |
| SIP `MEGAFON_SIP_PASSWORD` | Через личный кабинет МультиФон. Менять в окно когда нет звонков. |
| S3 Access/Secret Keys | Создать новую пару в Selectel, обновить rclone config, прогнать тестовый бэкап, отозвать старую пару. |

## 4. Чек-лист "куда положить новый секрет"

Когда подключаешь новый сервис (например, Salute Speech) и появляется новый ключ:

- [ ] Добавил в **пасс-менеджер** с понятным названием (`CRM / Salute Speech / API key`).
- [ ] Добавил в `.env.production` на сервере (НЕ в git!).
- [ ] Добавил **имя переменной** (без значения) в этот документ, в нужный раздел.
- [ ] Обновил `.env.example` соответствующего сервиса (пример со значением `your-key-here`).
- [ ] Прогнал `scripts/backup-env.sh` — новый зашифрованный `.env` улетел в S3.
- [ ] Назначил **уровень критичности** (C/H/M).
- [ ] Поставил напоминание в календарь на дату следующей ротации.

## 5. Что делать при компрометации (краткий runbook)

Допустим, ты увидел `BOT_TOKEN` в логах публичного сервиса. Порядок действий:

1. **Не паниковать** — паника приводит к ошибкам.
2. **Изолировать масштаб** — что ещё могло утечь? Если логи общие — возможно скомпрометированы все секреты, попавшие в логи.
3. **Ротировать скомпрометированный секрет первым** — по алгоритму из 3.3.
4. **Проверить access-логи** — кто-то уже воспользовался?
5. **Если да** — оценить ущерб (что прочитали, что записали, сколько потратили).
6. **Если нет** — выдохнуть, починить корень утечки (например, выключить debug-логирование секретов).
7. **Записать постмортем** в `docs/operations/incidents/` — что было, что сделал, что менять в процессе.
